# 方案三：成片后期链路提速 + 全链路「硬门槛 4 分钟 / 冲刺 3 分钟」总目标集成（提速方向 · v2 修订版）

> v2 修订说明：目标上调——**4 分钟为硬门槛，3 分钟为冲刺目标**（用户要求从严设定，开发时尽力冲刺）。v1 的「qc/gates 解码合并」被红队发现大半已实现、根因归属错误；4K 手段被实测改写。v2 重新归因并给出 3 分钟关键路径预算表。

## 〇、v1 → v2 的证据修订

1. **qc/gates「解码合并」大半已实现**：`scripts/content_gates.py:141-182` 已有 G2/G3+G7 单次解码合并 pass（含 `[timing]` 打点）。gates ~53s 的真实大头疑似 **G1**：每个口播窗/间隙窗各 spawn 一次 ffmpeg ebur128（`content_gates.py:53-55`，短窗 × 上百次进程），不是重复解码。v1 的 40s 目标手段用错了地方。
2. **真正漏掉的重复解码**：`vtx/qc.py:162` 响度检查 `ffmpeg -i final -af ebur128 -f null` **没有 `-vn`**，`-f null` 默认流选择连视频一起解码（`qc.py:160` 注释自认 ~60-90s 量级）——加 `-vn` 一行省掉整遍视频解码。且同一响度已在 gates G2、post_loudness、audio 回执测了 3-4 遍（`stages.py:315`、`cache/rerender_v40b.log:65`），共享一份测量即可。
3. **4K 实测改写**：现行命令确认是 lanczos + x264 medium 软件链（`runbook.md:54`），558s 全片 ~167s；scale_npp/cuda 路径在本机 ffmpeg 8.1.2 构建**不可用**（`--disable-libnpp`）；nvenc p6 反而比 p4 慢；**复用 vtx 分段机制 8 段并行 nvenc p4 实测 60s 片段 7.6s（236fps），外推全片 ~71s（2.3×）**。另外 4K 是发布动作（`runbook.md:163` R5 发布链），与验证链无数据依赖——**建议剔出冷跑关键路径**。
4. **QC 采样证明性跳过（新增方向）**：段内容键命中 = 该段与上次 QC 通过产物逐字节一致（内容寻址 + Chrome 确定性），命中段跳过像素探测在数学上成立；QC 从全片检变为「只检新渲段 + 全局元数据」。红队同时警告 `vtx/qc.py:62` 的像素比对只是 48×27 灰度缩略图，本就不是强门槛——golden hash 类强校验由方案一承担，QC 免检必须保留全局元数据检查。
5. **基线纪律（红队 M7）**：历史日志不可作验收基线——`rerender_v40b.log` 的 4K 141s 含断言耗时（口径不纯）、同名页 ms/帧跨日志差 2-8 倍、runbook 还写着「8 核」。所有性能验收必须当次同机重测、报 3 次中位、附分项计时。

## 〇b、开工前校准记录（2026-09-13 当次实测，执行纪律兑现）

基线纪律要求开工前当次重测。实测机器：RTX 4080 / 32C64G，空载（load <3），项目 bench_p2（voice-ime 同型 16746f/558.2s@1080p30），当日 ffmpeg 8.1.2。**三处 >20% 偏差，前提据此修正**：

1. **gates 大头归因再次改写**：v2 说「大头疑似 G1」——实测 gates 全量 36.6s = **G10 `-count_frames` 26.6s（72%）** + G2/G3+G7 合并 pass 5.4s + G1 仅 ~3.5s（63 个短窗 ebur128 逐 spawn 在本机 PCM 解码下并不贵）。对策修正：G10 帧数计数改 `-count_packets`（实测 0.12s，同值 16746；check_4k.sh 帧数门本就用 count_packets，仓内先例），收益 ~26s 比 G1 批量化（~3s）大一个数量级——G1 批量化降级为顺手项。
2. **qc 响度无 -vn 的代价被旧机口径夸大**：v2 说 ~60-90s——本机实测无 -vn 4.9s、加 -vn 0.4s（32 核 ffmpeg 8.1.2 视频链 ~3400fps）。仍改（一行、正确性更干净），但 qc 墙钟 10.7s 的关键路径是帧探测（~10s，8 线程并行），响度与探测并行——qc 墙钟收益预计 ≈0，响度共享的真实收益在温态二次验证与 gates 侧。
3. **当次全链基线 = 342s**（validate→gates，非 v2 记载的 ~445s，-23%）：串行头 6s / 并行波 177.2s（gfx 关键路径 177.2；audio 67.7、seg 预编码 47.9 波内重叠）/ video 尾 ~90s / post_loudness 2.6 / mux 4.3 / qc 10.7 / gates 36.6。v2 的 445s 是方案一/二落地前的多日志归并旧口径。4K x264 medium 当次实测 133.8s（v2 记载 ~167s，-20%）。
4. **预算表可行性核算（如实）**：本方案范围内全部落地后预估 ~310s——距 240s 硬门槛仍差 ~70s，缺口全部在方案一/二遗留项：gfx 波内 177s vs 单独口径 130s（波内 seg 预编码+audio CPU 争用 +47s；方案一 ≤110s 硬门本就未达，g6b 串行 ~80s 为已证硬下限）+ video 尾 90s vs 预算 ≤80s（方案二实测 threads 解锁无收益）。且 v2 预算表自身硬门槛加总 = 15+130+80+20+30 = 275s > 240s（表内隐含矛盾）。执行取向：本方案三阶段全部做满 + 总集成阶段做编排实验（波内并行度再平衡 A/B），最终以 bench_cold 实测报告，未达硬门槛按诚实条款如实判不通过并归因，不放宽数字。

## 二、推荐实施路线（指引性质，可按实际情况调整）

> 本节是调查时点的推荐路径，不是硬性要求。预算表是目标分解的参考框架，执行中可根据实测重新分配各阶段预算（例如 gfx 超预算时从 qc/gates 的富余中找回）——但第四节的总目标硬门槛不随之放宽，且实际路径与偏离原因须如实写入交付报告。
> **执行纪律（硬性）**：本规划不预设自己完全正确——路径推荐基于调查时点快照，先校准（开工前当次重测基线，与本文记载偏差 >20% 先修正文档前提再动手），再实施；判断标准是你自己的实测，不是文档断言。
> **组织方式（硬性）**：实施智能体作为**总控**对本方案交付质量负总责：尽可能把具体开发工作（写代码、跑实验、跑回归、写测试）派给**子智能体**执行，总控负责任务分解、派发（任务书自包含：目标/涉及文件/已知坑/完成定义/要求回传命令输出等证据）、裁定与验收；每个阶段性成果须由**未参与实现的独立子智能体**做对抗式审查（核原始日志、找验收可钻空子处、查协议与规范破坏），问题修复后复审关闭，审查报告随交付归档，总控不得审查自己派发的成果。
> **代码纪律（硬性，违反即审查不通过）**：风格与周边代码一致（命名/注释密度/`[timing]` 打点惯例），注释只写代码表达不了的约束；改动前读 `docs/DEV.md` 与 `skill/references/`，帧确定性协议、缓存键内容寻址语义、段边界机制不得绕过；行为改动带测试、性能改动带可复现基准脚本；小步提交、不绕过 lint/检查、实验代码收编或删除留结论；基线数字、证伪结论、新默认值写入 `docs/DEV.md` 与 runbook 之前，对应工作不算完成。

### 阶段 1：qc/gates 精修（1 天，性价比全表最高）
1. `vtx/qc.py:162` 响度检查加 `-vn`（一行，省整遍视频解码）。
2. 响度测量全链共享：audio 阶段回执的 LUFS/TP 结果按输入内容键存档（`cache/audio/`），gates G2 与 qc 响度项优先读回执，无回执才算；同一输入全链只测一次。
3. gates G1 窗口批量化：上百次短窗 ebur128 的逐窗 spawn 改为单进程多输入（或分批 ≤16 窗/进程），保留 `[timing]` 打点验证收益。
4. QC 命中段免检：段内容键命中且上次 QC 通过记录存在时跳过该段像素探测，只保留全局元数据检查（帧数/时长/响度/黑场抽检）；`--strict` 恢复全检。
   > **总控裁定（2026-09-13，审查后追认）**：免检记录由「全检全过才写」改为**「按检查项记忆」**——免检仅对「上轮该检查项 pass 且其覆盖段文件 (size,mtime_ns) 与记录一致」生效（✗ 项永远实测），记录另绑定 final.mp4 的 (size,mtime_ns)（重封装即整体失效全检）。动因：bench_p2 的 c4_mini 为已证伪探针假阴性恒 ✗（DEV.md 方案二先例），原口径下记录永不建立、温态免检永不生效。独立审查对抗攻击结论：证据链（上轮 pass + final stat 不变 + 段 stat 不变）与全过门同一内容绑定强度；纯音频变化经 final stat 绑定闭环失效；75 项 checks 名称序列免检/全检/--strict 三态逐项全等，「免检悄悄少检」不存在。黑场检查由 gates G7 全片 blackdetect 每轮实测承担（强于原文「黑场抽检」措辞）。验收 1 的「75 项 QC 全过」按 bench_p2 实际口径为 74/75（c4_mini 假阴性，DEV.md 已收编）。

### 阶段 2：4K 发布链重做（1 天）
5. 复用 vtx 分段机制实现 4K 导出：8 段并行，每段 `scale=3840:2160:flags=lanczos + h264_nvenc p4`，concat `-c copy`；实测外推 ~71s。规格断言（分辨率/帧数/时长）保持。
6. 4K 从 `bench_cold` 主线剔出，单列「发布链预算」；提供 `--with-4k` 一键含入。
7. 画质门禁：与软件 x264 medium 基线抽样对比（≥5 帧）PSNR ≥42dB 或 SSIM ≥0.99。

### 阶段 3：总集成与冷跑基准（1 天）
8. `scripts/bench_cold.sh`：真实清理全部缓存 → 分项计时跑 validate→…→qc→gates（4K 默认出列）→ 输出各阶段耗时表 + 关键路径合计，存 `cache/bench_cold_<date>.log`。每阶段内打 `[timing]` 分项点（gfx 路径打标来自方案一）。

10. 更新 runbook 耗时基准表（含修正「8 核」等过时信息）与 SKILL.md 冷跑预期，让智能体对全量验证耗时有一致预期。

## 三、开发要求

1. 4K 交付规格不变：3840×2160、30fps、帧数与母带一致、断言全过。
2. QC/gates 检查项一项不减：G1/G2/G3/G7/G10 全保留，黑场/真峰灵敏度不下降（历史黑屏样本回归）；QC 免检只对内容键命中段生效且 `--strict` 必须恢复全检。
3. 响度共享必须以内容键为前提——音频输入任何变动使回执失效重测，禁止跨版本复用数字。
4. bench_cold 必须真实清缓存（gfx/seg/段/音频/回执），不允许假冷跑。
5. 与方案一/二叠加不冲突：流水线化（方案二）下的分项计时仍可归因到阶段。

## 四、验收要求（严格、可量化、防自夸）

> **总验收是本方案核心交付**。所有数字来自 `bench_cold.sh` 当次输出，3 次取中位，日志原文随报告提交；基线当次同机重测，禁止引用历史 log。

1. **qc/gates 提速**：qc+content_gates 合计 **≤30s**（当次基线 ~65s±20%），且 75 项 QC 全过、五门全绿、黑场复测样本零漏报、`--strict` 模式下检查项数量与免检前一致（计数断言）。
2. **4K 发布链**：`--with-4k` 下 4K 生成 **≤80s**；画质门禁 PSNR/SSIM 达标；规格断言全过。
3. **硬门槛**：`bench_cold.sh` 验证链（validate→gates，不含 4K）墙钟 **≤240s**。
4. **冲刺目标**：验证链墙钟 **≤180s**；未达不判整体失败，但必须输出逐阶段实际值 vs 预算表的对照与缺口归因（哪个阶段的哪一项未落地）。
5. **可复现性**：连续 2 次总耗时均达标且阶段波动 <15%。
6. **免检正确性（硬门槛）**：构造一个「段缓存命中但产物被篡改」的反例（手工改写段文件不改键），QC 免检模式必须仍能通过全局元数据检查发现异常或明示免检风险；篡改段在 `--strict` 下必须被抓。
7. **诚实条款**：验收报告附完整 bench 日志（含失败重试与 [timing] 分项），禁止摘录拼贴；任一硬门槛未达即整体判不通过，不得宣称「基本达标」。
