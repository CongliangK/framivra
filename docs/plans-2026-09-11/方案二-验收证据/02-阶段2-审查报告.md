## 必做核查 1：代码精读（git show 1a3206e）

### audio --report 与流水线（重点怀疑项）——**不成立，无 P1**
- `vtx/vtx.py:452`：`if (a.report or a.report_only) and a.command != "audio": ... sys.exit(1)`——`--report` 是 audio 专属硬门，`vtx all --report` 在进入编排前即被拒绝。
- **真机验证**：`vtx.py --report -t timeline.json all` → 输出「--report/--report-only 仅作用于 audio 阶段」，退出码 1。不存在「流水线静默丢报告」路径。
- 线性分支里的 `if name == "audio" and a.report` 保留原位（vtx.py:589 附近，重构后仍在 else 线性分支内逐字未动）；且 `command=="audio"` 永不进入流水线分支，逻辑自洽。

### `_run_all_pipeline` 与线性循环逐语义一致性——**一致**
- 串行头/尾的 `print == name ==` → `begin_stage(_stage_receipt_name(...))` → `RuntimeError → print ✗ + sys.exit(1)`，与线性循环同构；`_stage_receipt_name` 是从线性循环原内联规则抽出的 helper（`name + "_draft" if draft and name in ("video","mux")`），两处单一权威，测试覆盖 draft/非 draft/无关阶段全组合。
- 依赖门判定条件、DOWNSTREAM 撤销逻辑在 begin_stage 内部（infra.py），未被触碰。
- 波内 `_stage_job`：`begin_stage → RuntimeError → sys.exit(1)`，线程内 SystemExit 只杀线程，由 run_wave 捕获记失败表统一退出——语义与线性路径的失败即退等价（见核查 2 失败注入）。
- STAGES 名集与三段划分（validate/audit/prepare + gfx/audio + video/mux/qc）一致，`by_name` 全覆盖 8 阶段。

### `c._pre_layers` 与 dry-run——**不炸**
- `prepare_layers`（composite.py:329）不读 `c.dry` 分支返回值：层对象照常构建返回，ffmpeg 编码任务经 `Ctx.run` 的 dry 守卫（infra.py:59 `[dry-run]` 打印）跳过；`build_video(layers=...)` 传入的 layers 是纯数据，dry 下 video 段切片同样走 dry 打印。真机 dry-run（`--dry-run all`）跑通至 qc 跳过探测、正常打印「完成」。
- `getattr(c, "_pre_layers", None)` 兜底：仅当波失败时才可能缺属性，而波失败已 `sys.exit(1)`，串行尾不可达——兜底实际不可达，纯防御，无害。

### run_wave 失败语义——**符合声明**
- `except BaseException`（含 SystemExit）逐 job 捕获；`failed` 列表 append（GIL 原子）；join 后报**首个**失败标签与异常到 stderr，`sys.exit(1)`。失败时**其余两路跑完再退**（取消进程树复杂度不值的明示取舍，docstring 写明）。

### receipt 锁——**正确，无死锁**
- `receipt()` 与 `begin_stage()` 的读-改-写整段持同一实例锁 `Ctx._receipt_lock`（infra.py），`with` 语义保证锁内 raise（依赖门 RuntimeError）时锁正确释放。
- 无嵌套持锁：begin_stage 锁内只做 load_receipt/pop/write，不调用 receipt()；两方法互不调用；每 Ctx 一把锁，无跨对象顺序问题——死锁不可能。

### 波内失败可归因性（真机，见核查 2）——audio 失败归因清晰，gfx/video 预编码跑完，退出码 1。
