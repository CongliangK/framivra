## 1. 脚本质量（scripts/bench_cold.sh）

### 1.1 gawk 时间戳写法 — 正确工作 ✓
`gawk '{ print systime()" "strftime("%T",systime())" | "$0 > "/dev/stderr"; fflush() }' 2> "$LOG"` 实测产出正确：每轮日志 239 行，首行格式 `1789195421 14:43:41 | == validate ==`，epoch 整数秒 + 人类可读时间 + 原始行，逐行无缓冲丢失。三条日志首行/末行 epoch 均单调递增。

### 1.2 摘要提取 — 能用但有两处粗糙
- `head -1 | awk -F' \\| '` 的「起:」打印的是**首行内容**（`== validate ==`）而非时间，「止:」同理打印 `QC：74/75 通过`——展示误导，但全链墙钟用 `cut -d' ' -f1` 取 epoch 计算，数值正确（281/302/299 均复核一致）。
- 若 vtx 中途崩溃、末行非 QC 行，END-START 仍成立，健壮性尚可。
- **NIT**：脚本注释写「tee 到日志」，实际 vtx 输出全部进了日志文件，控制台看不到进度（tee 语义名不符实）。
- **NIT**：日志名仅含日期（`vtx_bench_YYYYMMDD_rN.log`），同日重跑会覆盖旧日志，历史基准不可追溯（本次审查依赖的正是这些 /tmp 日志）。
- **NIT**：未检查 gawk 依赖；mawk（Debian 默认）无 systime/strftime，脚本会静默产出坏日志。

### 1.3 set +e / set -e — 正确 ✓
`set +e` → 管道 → `VTX_RC=$?` → `set -e` 恢复。注意 `pipefail` 在顶部已设且 `set +e` 不影响 pipefail，故 `$?` 正确反映 python 的失败（而非 gawk 的成功）——这个细节做对了。

### 1.4 `rm -rf "$PROJ/cache"` 防呆 — 可接受，但有缺口（P2）

## 3. PSNR 对照方法攻击 — 方法成立，数据复算全中，但计数有一处错

### 3.1 帧对齐 ✓

### 3.2 归档数据与源文件一致性 ✓
用独立命令从 baseline_threads1/final.mp4 与 out/final.mp4 重新抽帧，md5 与 /tmp/psnr_cmp/old_*/new_* **逐字节一致**（old_01=500、old_03=2092、old_06=3000 均匹配）——归档 PNG 确实出自这两个成片，抽帧方法可复现。

### 3.3 独立复算 PSNR ✓（抽 4 帧）
- f2092（声称 min 40.40）：独立复算 **average:40.395951** — 与 result.txt 完全一致。
- f500：复算 **49.657038** — 一致。
- f3000 / f4187 / f16500 / f4185 / f10465 / f12559（result.txt 空值=inf 帧）：独立抽帧 **byte-identical** — inf 判定（逐位相同）成立。
- 有限值中位复核：12 个有限值排序中位 ≈41.52 ≈ 文档 ≈41.5 ✓；范围 40.396–50.136 ≈ 40.4–50.1 ✓。

（审查过程注记：曾用单条 ffmpeg 双输出命令抽帧得到错误的「全 identical」，改为逐文件独立抽取后与归档吻合——实施者的归档方法是对的。）

### 3.4 「差异源只有 seg 编码器」— 基本成立，一处未闭合（P2 备注）
- threads 形态：两代成片均 x264 medium、段拼接形态相同；渲染流水线不改。
- vseg（分段渲染中间物）两代均 h264（`cache/vseg/seg00_*.mp4` 与 `baseline_threads1/vseg/seg00_*.mp4` codec 均 h264），段渲染编码代未切换。
- 未完全闭合点：vseg 两代 h264 的**编码参数是否完全相同**未逐项比对（本次未做）；若方案二期间动过段渲染编码参数，归因会掺入杂质。现有证据下归因「clip seg 预编码代差」是合理的，但严谨措辞应保留「以 vseg 编码参数未变为前提」。

### 3.5 「不可见级」措辞 — 基本公允，略强（P2）
- 采样偏保守：31 帧 = 7 切点边界 ±1（21 帧，最坏区）+ 10 随机，min 恰落在边界帧 f2092——拿最坏处说话，方向诚实。
- 但 40.4dB 单帧在细纹理/字幕边缘区**可能**被注意（PSNR 与主观感知非线性，>40dB 是「高质量」经验带而非「不可见」保证）；支撑「不可见级」更强的证据其实是 **19/31 帧逐位相同**——代差大部分帧根本不存在，而非「存在但小」。DEV.md 现措辞「编码器代差在成片为不可见级」可接受，但若改为「多数帧逐位相同、最坏边界帧 40.4dB（高质量带）」更严谨。

### 3.6 计数错误（P2）：**inf 应为 19 帧不是 18 帧**
result.txt 31 行 = 12 有限 + **19 空值（inf）**。DEV.md 与 commit message 均写「18 帧逐位相同，其余 12 帧」= 30 帧，与「抽 31 帧」自相矛盾，且与实际数据差 1。结论不受影响（40.4–50.1、min、中位均对），但数字须订正为 19/12。

## 7. 专项判定：r2/r3 起跑 load 残留（17-21）是否污染中位

**判定：不影响结论，方向偏保守。**

证据：
1. 干净起步的历史 gfx 冷跑：172.1s（阶段2，等负载<3）、171.6s / 187.2s（阶段3 两轮，等负载<3）。本轮 r1（干净）161.9s 反而是全历史最快——与 NVENC 卸载 CPU 编码、缓解 gfx 竞争的机制自洽；r2/r3 的 181.7/179.9 落在历史 171.6–187.2 分布带内，**没有超出历史方差的系统性偏慢**。
2. 残留影响的量级估计：r1 161.9 vs r2/r3 ~180，残留 load 至多给 gfx 加 ~10%，对全链 ~5-6%。若三轮全部空载，中位估计 ~285-292s——**只会更好看**。
3. 关键的 -20% 头条用的是三轮中位 299 vs 375；即使拿最差的 r2=302 计也是 -19.5%，结论对残留负载不敏感。
4. 但这是**基准方法缺陷**：sleep 10 达不到任务书 load<3 口径，中位数被残留抬高而非压低（保守方向），若日后有人只跑 1-2 轮可能采到脏样本。**P1（方法）：bench_cold.sh 应改为轮间等待 load<3（如 `while [ $(cut load) > 3 ]: sleep`），而非定时 sleep 10**；本轮数字可保留定版，附「r2/r3 起跑 load 17-21，中位偏保守」备注更佳。
