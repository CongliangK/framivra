# 方案二：合成链路提速——filter 多线程解锁、seg 编码与流水线化（提速方向 · v2 修订版）

> v2 修订说明：v1 的两条核心假设被实测证伪（gfx 中间产物视频化、音频测量缓存），替换为本轮实验**新解锁的最大杠杆**：`-filter_complex_threads 1` 已过时。目标：video+audio 阶段 ~150s → **≤70s（硬门槛）**。

## 〇、v1 → v2 的证据修订（实施前必读）

本机实测（子智能体实验，2026-09-11，ffmpeg 8.1.2 / RTX 4080 / 32 核）：

1. **`-filter_complex_threads 1` 竞态已不复现（v1 最大遗漏）**：`composite.py:205-219` 注释记载 v3.6 61 层 framesync 竞态故强制单线程；实验用 61 层 ±20 帧密集端点复现图测试，threads=1 与 4 输出 MD5 完全一致，且 **threads=4 快 2.0×**（14.0s vs 27.8s）。改为默认 4 + 帧数自检兜底（已有）可给滤镜主链免费 2×。
2. **gfx 中间产物视频化（v1 核心）证伪**：PNG 序列经 ffmpeg 解码仅 0.45-4.8ms/帧（SIMD 多线程），非瓶颈；FFV1/rawvideo 中间格式最多省 0.2s/240 帧却要 3.1MB/帧磁盘（90s 段 ≈8.3GB）。**不做**。v1 验收 4 的「mov vs PNG 逐帧 diff==0」红队也指出按设计不可能（RGB→YUV 量化误差），两项一并撤销。
3. **音频测量缓存证伪**：ebur128 测量遍实测仅 0.37s（v1 以为占 26.6s 的一半），缓存最多省 <1s，**不做**。音频 26.6s 的真实构成是 72 路 wav 解码 + 大 graph 本身，优化空间留给流水线化（与 gfx 并行）而非内部改造。
4. **seg 预编码 x264→NVENC 只省 ~13%**（2.82s→2.46s/千帧）：瓶颈是 4K 源解码（50%）+ 缩放（18%），不是编码。NVENC 化降级为低优先级顺手项。
5. **NVENC 并发拐点 = 8**（聚合上限 ~1100-1150fps 1080p，8→12 无收益）：`VTX_VIDEO_SEGMENTS=8` 已是最优，**不上调到 12/16**。需要设计的是**全局 NVENC 会话预算**（红队 M2：段渲染 8 并发与 4K 导出/其他 NVENC 任务同时抢会话会互相触发回落串行）。
6. hwupload_cuda 维持负收益结论。

## 一、现状与根因（修订后）

> **开工校准（2026-09-12 实施总控当次重测，32C/RTX 4080/ffmpeg 8.1.2，voice-ime 现行 timeline 16746f/69 层，/tmp 逐行时间戳冷跑）**：
> 本表 ~90s 前提**成立**——其形态为 `--gpu`（NVENC p7，即生产形态）：当次重测分段+concat **89s**（偏差 -1%）。x264 medium（`vtx all` 无 --gpu 默认形态）为 126s。seg 预编码 33s ✓、audio 27s ✓、gfx 全冷 165s；61 层密集端点图复现 **threads=1 26.17s / threads=4 13.54s（MD5 逐位一致，耗时比 0.52）**。
> **但核心杠杆在真实管线被证伪（阶段1 实测，详见 DEV.md §二）**：8 段并行下 threads=4 墙钟收益仅 89→86s（--gpu）/ 99→98s（x264），2× 只在单进程大 graph 成立；且真实项目前 3 段存在与线程数无关的跨运行非确定性（threads=1 同 argv 复渲 4 次 4 个 md5），验收 4 的逐帧 diff==0 门在 t1 控制组即不可复现。默认维持 1，`VTX_FILTER_THREADS=4` 显式开启。验收 1 的 ≤55s 与验收 2 的 ≤70s 据此判**不可达**，按诚实条款 7 如实报告实测数字。

| 子阶段 | 现状 | 修订后根因 |
|---|---|---|
| 8 段并行合成 + concat | ~90s（--gpu 形态；09-12 重测 89s ✓，x264 形态 126s，见上注） | 滤镜主链被 `composite.py:219` 强制单线程（基于已过时的竞态记录），单段 CPU 利用率仅 ~7.8%（⚠ 阶段1 实测修正：解锁后真实管线无墙钟收益，根因另有其详） |
| seg 预编码（41 clips） | 33-36s | 4K 源解码 50% + lanczos 缩放 18% + x264 编码 ~32%；已 6 线程并行 |
| audio 混音 | 26.6s | 72 路 wav 解码 + 大 graph；无廉价内部优化空间 |
| 阶段间串行 | — | seg 预编码（只依赖源视频）、audio（只依赖音频源）与 gfx **零数据依赖**，却串行等待 |

## 二、推荐实施路线（指引性质，可按实际情况调整）

> **执行纪律（硬性）**：本规划不预设自己完全正确——路径推荐基于调查时点快照，先校准（开工前当次重测基线，与本文记载偏差 >20% 先修正文档前提再动手），再实施；判断标准是你自己的实测，不是文档断言。
> **组织方式（硬性）**：实施智能体作为**总控**对本方案交付质量负总责：尽可能把具体开发工作（写代码、跑实验、跑回归、写测试）派给**子智能体**执行，总控负责任务分解、派发（任务书自包含：目标/涉及文件/已知坑/完成定义/要求回传命令输出等证据）、裁定与验收；每个阶段性成果须由**未参与实现的独立子智能体**做对抗式审查（核原始日志、找验收可钻空子处、查协议与规范破坏），问题修复后复审关闭，审查报告随交付归档，总控不得审查自己派发的成果。
> **代码纪律（硬性，违反即审查不通过）**：风格与周边代码一致（命名/注释密度/`[timing]` 打点惯例），注释只写代码表达不了的约束；改动前读 `docs/DEV.md` 与 `skill/references/`，帧确定性协议、缓存键内容寻址语义、段边界机制不得绕过；行为改动带测试、性能改动带可复现基准脚本；小步提交、不绕过 lint/检查、实验代码收编或删除留结论；基线数字、证伪结论、新默认值写入 `docs/DEV.md` 与 runbook 之前，对应工作不算完成。

### 阶段 1：滤镜多线程解锁（1 天，最高性价比）
1. `composite.py:219` 硬编码 `-filter_complex_threads 1` 改为可配置（env），默认 4。
2. 回归验证：用 v3.6 病灶形态的 61 层密集 graph 复现测试（实验脚本已在 /tmp/bench，收编入 `tests/`）+ 整片 `vtx all`，帧数自检（`composite.py:312`）+ qc 全过 + 与 threads=1 产物抽样逐帧 diff==0。**任何一段 diff 非零即回退默认值并在 DEV.md 记录。**

### 阶段 2：跨阶段流水线化（1-2 天，确定性收益 ~63s）
3. `vtx.py` STAGES 从线性序列改为依赖图：`prepare → (seg 预编码 ‖ audio ‖ gfx)` → video → mux → qc。seg/audio 与 gfx 完全重叠，关键路径直接省 ~63s。
4. 实现用现成 `infra.run_parallel` 机制（~50 行改动）；阶段日志按流水线交错输出但分项计时必须保留可归因。
5. 注意写冲突（红队 M4）：`hygiene.py` 的 manifest 记账持全局锁且每笔全量重写（`hygiene.py:99-122`），流水线并发下改为 append-only JSONL 或细分锁；`versions_record` 对 GB 级文件全量 md5（`hygiene.py:22-29`）移到 strict 模式或后台。

### 阶段 3：seg 预编码 NVENC 化（顺手项，半天）
6. `composite.py:370` 无 alpha seg libx264 → h264_nvenc p4（只省 ~13%，但免费）；alpha 段保留 ProRes 4444 不动；失败自动回落。
7. **全局 NVENC 会话预算**（新设计）：在 `encoders.py` 增加进程内会话计数器，段渲染（8）、seg 预编码并行、4K 导出共享预算，防止叠加任务互相触发探测失败回落串行。

### 阶段 4：回归与文档（半天）
8. 全链冷跑基准（用方案三的 `bench_cold.sh`）+ golden 段边界 diff；更新 DEV.md（记录 threads=1 竞态证伪结论与 NVENC 拐点数据）与 runbook。

## 三、开发要求

1. **帧精确性不可妥协**：段边界机制、`SEG_CUT_GUARD`、`-c copy` concat、总帧数硬自检全部保持；threads=4 的引入必须以「61 层复现图 + 整片全段抽样 diff==0」为放行条件。
2. 画质交付标准不变：最终成片 NVENC p7 h264 1080p；中间件改动不允许在 QC 出现新差异。
3. alpha 段（opacity/fade）继续走 ProRes 4444 CPU 路径，不受 NVENC 化影响。
4. 流水线化不得改变各阶段产物语义与缓存键；并发下的缓存记账必须正确（并发压力测试：流水线模式跑 3 次无 manifest 损坏、无重复渲染同一内容键）。
5. 每项优化独立开关可 A/B；NVENC 拐点（8）写入文档防止后人误调。

## 四、验收要求（严格、可量化、防自夸）

> 性能数字来自 `bench_cold.sh` 当次冷跑（清全部相关缓存），报 3 次中位；基线当次同机重测。

1. **滤镜多线程（硬门槛）**：61 层复现图 threads=4 vs 1 输出 MD5 一致且耗时比 ≤0.6；整片分段合成+concat 阶段耗时 **≤55s**（基线 ~90s 当次重测）。
2. **流水线化（硬门槛）**：冷跑日志显示 seg 预编码与 audio 阶段完全落在 gfx 阶段墙钟窗口内（时间戳为证），video+audio 关键路径合计 **≤70s**。
3. **seg 预编码**：41 clips ≤30s（NVENC 化后），无 alpha 段编码器字段为 h264_nvenc。
4. **像素一致性（硬门槛）**：threads=4 整片产物与 threads=1 基线全段抽样（≥5 段）逐帧 diff==0；QC 75/75 且 qc diff 无差异项。
5. **帧数自检**：concat 后总帧数 == duration_frames 断言通过。
6. **并发正确性**：流水线模式连续 3 次冷跑，manifest 无损坏、无同内容键重复渲染；NVENC 会话预算在段渲染+4K 叠加场景下无互相回落串行（日志为证）。
7. **诚实条款**：threads=4 若任何段 diff 非零，必须回退并记录，不得放宽 diff 阈值硬上；所有未达硬门槛的项在报告中列明实测数字。
