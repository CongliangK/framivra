> 2026-09-11 第二轮调查的原始结论存档。**本文档不作为实施依赖**：执行智能体只会收到单份方案文档，所有硬性要求（执行纪律、组织方式、验收门槛）已内联在各方案文档中；本文档仅供人类回顾调查依据与证伪清单时查阅。

## 执行须知（原稿，硬性内容已内联至五份方案文档，此处仅存档）

以下三条原则在每份方案文档的「推荐实施路线」引言中均已内联，此处保留原稿供追溯：

1. **本规划不预设自己完全正确。** 这些文档形成于开发之前，其中的数字、根因归因、路线步骤都基于调查时的快照，可能随你的开发推进而过时或被证伪——本规划的 v1→v2 修订本身就是活例（原方案的 4 条核心假设被实测推翻）。
2. **目标与验收是硬性的，路径是弹性的。** 各方案「验收要求」章节中的量化门槛（性能数字、像素一致性、诚实条款等）必须达成，不允许协商；但「推荐实施路线」章节只是调查时点上的最优猜测，**明确授权你根据实际情况调整、替换甚至放弃其中的具体步骤**——只要你最终拿出满足验收的结果，并如实记录你实际走了哪条路、为什么偏离推荐。
3. **开发中发现新的更大杠杆时，放手去抓。** 如果你在实施中发现文档没提到的瓶颈或优化机会，且它对目标的贡献大于文档路线中的某项，可以替换优先级；反之若发现某条「已证伪勿再试」清单之外的路也走不通，把它补进证伪记录（`docs/DEV.md` 与本总纲），这是对后续迭代者的实质贡献。
4. **先校准，再动手。** 实施任何方案前，先用该方案规定的基线方式（当次同机重测）确认现状数字；若现状与文档记载偏差 >20%，先更新文档中的基线再开工，避免在错误前提上做优化。
5. **判断标准永远是你自己的实测**，不是文档里的断言——包括本文档。文档里的「已证伪」清单是帮你省时间的，不是禁止你复核的；有怀疑就花几分钟重测。

## 执行组织方式（总控负责制 + 子智能体开发 + 对抗式审查）

接受本规划的实施智能体（下称**总控**）按下述方式组织整个开发过程，这是硬性要求而非建议：

### 1. 总控职责：统筹与裁定，不亲写实现代码
- 总控对全部方案的最终交付质量负总责：分解任务、派发子智能体、裁定分歧、维护文档与现实的一致、把控验收。
- **尽可能把所有具体开发工作（写代码、跑实验、跑回归、写测试）交给子智能体执行**，总控不亲自堆实现细节。理由：①并行提速——各方案、各阶段、互不依赖的实验可以多子智能体同时推进；②上下文质量——子智能体带着单一明确任务启动，比总控在长会话里串行处理多任务更不容易遗漏；③总控保留全局视野做跨方案裁决（如 NVENC 会话预算这类跨方案共享资源）。
- 派发子智能体时给出**自包含任务书**：目标、涉及文件、已知坑（含本总纲的证伪清单）、完成定义、需要回传的证据。子智能体的最终消息是回传给总控的唯一通道，任务书里必须要求它附上可核查的证据（命令输出、日志路径、测试结果）。

### 2. 每轮开发完成后必须过对抗式审查
- **节奏**：每个子智能体交付一项阶段性成果（一个阶段完成、一个优化开关可 A/B、一个命令可用），即触发一轮审查，不等全部开发完才审。
- **审查方式**：派出**独立审查子智能体**（未参与该实现的），以红队姿态攻击成果：数字是否真的达标（要求附原始日志）、验收条款是否有被钻空子的解释、改动是否破坏帧确定性/缓存键语义/项目规范、有没有「技术上达标但实际无意义」的通过方式。
- **审查结论处置**：发现的问题由总控开新任务书派子智能体修复，修复后**复审**直至关闭；审查发现推荐路线前提失效时，总控负责更新对应方案文档。审查报告与处置记录随交付归档，禁止「审查发现的问题不记录直接改掉」。
- 总控自身不得兼任自己所派发成果的审查者；规模小的阶段可以合并审查，但每个方案至少各有一次独立审查记录。

### 3. 代码纪律与项目规范（贯穿全程，违反即审查不通过）
- **遵循仓库既有风格**：改动读起来像原有代码——命名、注释密度、错误处理、日志格式（含 `[timing]` 打点惯例）与周边一致；注释只写代码本身表达不了的约束，不写「本次改了什么」。
- **遵守项目既有约定**：改动前先读 `docs/DEV.md`（演进与证伪记录）、`skill/references/`（协议与配方）、仓库 README；协议类约束（gfx 帧确定性三禁则、缓存键内容寻址语义、段边界机制）不得绕过。
- **测试与回归随代码走**：行为改动必须带对应测试（含回归测试，参照 `tests/` 既有写法）；性能改动必须带可复现的基准脚本/命令，且回归测试在任何优化开关关闭时保持通过。
- **提交纪律**：小步提交、每步可独立回退；不用 `--no-verify`、不绕过 lint/格式检查；临时实验代码不进主分支，实验脚本要么收编为正式工具/测试，要么删除并记录结论。
- **文档同步是完成定义的一部分**：基线数字、证伪结论、新默认值写入 `docs/DEV.md` 与 runbook 之前，对应工作不算完成。

## 一、目标设定（从严）

- **硬门槛**：全链无缓存冷跑（验证链，不含 4K）≤ **240s（4 分钟）**。
- **冲刺目标**：≤ **180s（3 分钟）**——用户要求目标从严设定；3 分钟蓝图见方案三预算表，达成条件主要是 gfx ≤75-90s（方案一 canvas 批量导出）+ qc/gates ≤20s。
- 4K 投稿版剔出验证链关键路径，单列发布链预算 ≤80s（8 段并行 nvenc p4 实测外推 ~71s）。

## 三、实测实验结论（子智能体 /tmp/bench，本机 32 核 + 4080 + ffmpeg 8.1.2）

**证实的假设**：页级并行近线性（2 实例 1.64×）但 6 页后 CPU 饱和；NVENC 并发拐点 = 8（聚合 ~1100-1150fps，8→12 无收益）；VTX_VIDEO_SEGMENTS=8 已是最优。

**证伪的假设（勿再投入）**：
- 逐帧导航是 gfx 瓶颈（只占 ~8-15ms/帧；截图通路 ~50ms/帧才是，空白页同价，换格式/裁剪无效）
- PNG→FFV1/rawvideo 中间格式（PNG 解码仅 0.45-4.8ms/帧；FFV1 慢 5 倍 + 3.1MB/帧磁盘）
- 音频 ebur128 测量缓存（测量遍实测仅 0.37s，缓存省 <1s）
- scale_npp/scale_cuda 全 GPU 4K 链（本机 ffmpeg 构建不支持 libnpp/cuda hwaccel）
- seg 预编码 x264→NVENC 大幅提速（只省 ~13%，瓶颈是 4K 解码 50% + 缩放 18%）

**新解锁的杠杆（v2 新增，按性价比排序）**：
1. `-filter_complex_threads 1` 竞态在 ffmpeg 8.1.2 不复现：61 层复现图 threads=4 输出 MD5 一致且快 2.0× → 滤镜主链免费 2×（方案二阶段 1）
2. 页内 canvas toBlob 导出 13-29ms vs 截图 50ms，且可批量回传 → gfx 主攻方向（方案一阶段 2）
3. seg 预编码 / audio 与 gfx 零数据依赖，流水线化直接省 ~63s 关键路径（方案二阶段 2）
4. 4K 复用 vtx 分段机制 8 段并行 nvenc p4：167s→~71s，或整体剔出关键路径（方案三阶段 2）
5. qc.py:162 加 `-vn` + 响度测量全链共享 + gates G1 批量化（方案三阶段 1，~0.5 天换 ~40s）
6. QC 命中段免检（内容寻址的证明性跳过，须保留全局元数据检查与 --strict 全检）（方案三）
7. 次级：静态跨度声明协议（gfx 帧平均 ~20% 字节级重复，最高 74%）、manifest 记账 append-only 化、versions_record md5 移出热路径

## 四、横切纪律（所有方案通用，红队 M7/S4）

1. 性能验收一律**当次同机重测基线**，禁止引用历史 log（历史日志同名页 ms/帧差 2-8 倍，runbook 还写着「8 核」，4K 141s 基线含断言耗时口径不纯）。
2. 报告 3 次中位数而非单次最好值；每阶段 `[timing]` 分项计时打点（仿 content_gates.py）。
3. NVENC 全局会话预算：段渲染、seg 预编码、4K 导出共享，防止叠加任务互相触发回落串行。
4. 强像素门槛用 golden hash（QC 的 48×27 灰度比对检测不出字体缺失/颜色偏移，不设防）。
5. 每份方案含诚实条款：任一硬门槛未达必须报告实测数字与归因，探路实验失败也要记录。

## 五、3 分钟蓝图关键路径（详见方案三）

```
validate/prepare ~15s │ gfx ≤75-90s（canvas 批量导出）│ seg/audio 与 gfx 流水重叠
段合成 ≤50s（threads=4）│ mux ~5s │ qc+gates ≤20s（-vn+共享+G1 批量+免检）│ 合计 ~185s
```

最大不确定性：① gfx 聚合吞吐在 canvas 改造后的实际上限（foreignObject 字体保真需逐页探路）；② threads=4 在真实 69 层 graph 的长尾稳定性（复现测试必须先行）。
