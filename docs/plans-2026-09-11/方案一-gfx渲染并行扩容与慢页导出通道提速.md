# 方案一：gfx 渲染提速——canvas 批量导出主攻 + 并行扩容辅助（提速方向 · v2 修订版）

> v2 修订说明：v1 假设「并行扩容 6→12 得 1.6-2×」被红队证伪（见 §0）；经子智能体实测，本方案主攻方向改为**绕开 captureScreenshot 固定通路的 canvas 批量导出**。目标：gfx 冷跑 192.5s → **≤110s（硬门槛）/ ≤85s（冲刺）**。

## 〇、v1 → v2 的证据修订（实施前必读，防止走回头路）

以下为本机实测（子智能体实验，`/tmp/bench/`）与红队核查结论：

1. **有效加速比已近饱和**：`cache/gfx_cold_bench.log` 逐页耗时求和 840.7s ÷ TOTAL_WALL 192.5s = **4.37×**（PAGES=6 下），各页 ms/帧已被争用抬高（单页基线 ~34-50ms/帧，bench 中 c5a 达 136ms）。页级并行外推上限 ~5.5-6×，**单靠并行只能到 ~150-170s，到不了 96s**。
2. **逐帧导航不是瓶颈**（v1 红队猜想 F2 部分证伪）：每帧导航+重执行只占 ~8-15ms/帧，captureScreenshot 本身 ~50ms/帧（空白页同为 51.5ms，**与内容无关的固定通路开销**）；jpeg/webp/裁剪均无收益。
3. **canvas toBlob 是真杠杆**：页内 canvas 导出同等内容仅 **13.3ms（中）/ 29.2ms（重）**，比截图快 1.7-3.8×；且可在页面内连渲 N 帧后批量回传，绕开截图通路。
4. **tab 级并行 4→8 仅再快 19%**（透明页 alpha 合成持 GIL），**tab 数保持 4**，扩展单位是浏览器实例；实测 6 实例时 CPU 已饱和（合计 ~49.6fps，相对 3 页仅 +45%），内存 ~1.1GB/实例，12 实例 ≈13GB 在 64G 内存下可行但收益递减。
5. 已证伪勿再试：GPU 光栅、screencast、virtual-time、MediaRecorder、omitBackground、截图换格式/裁剪、PNG 中间格式替换。

## 一、现状与根因

- 入口 `vtx/vtx.py` gfx 阶段；CDP 后端 `vtx/gfx_render.py`：常驻 headless Chrome（`--disable-gpu`）+ 每 tab 一条 WS 连接，每帧 `Page.navigate(?f=N)`（`gfx_render.py:479`，导航内 20ms 轮询 `gfx_render.py:251-267`）→ `Page.captureScreenshot`（L479-502）。默认 4 tabs（L455），页级并行 `VTX_GFX_PAGES=6`（`vtx.py:128`）。
- alpha 页已有多通道：`Emulation.setDefaultBackgroundColorOverride(a=0)` 单截快路径（L488-495）、`window.__vtx_export_png()` canvas 导出通道（L404-443，**协议已预留，只差页面接入与批量回传**）、flatten 守卫回落双截（L569-591）。
- 基准：12024 帧冷跑 192.5s；慢页 c5a_main_path 136ms/帧。**日志未记录每页实际走的导出路径**（快路径/canvas/双截），这是 v2 要先补的观测。

### 阶段 0：观测与基线锁定（半天）
1. `gfx_render.py` 为每页日志增加**路径打标**（override 快路径 / canvas / 双截回落 / body-opacity flatten）与每帧分项计时（导航/截图或 toBlob/编码/落盘），仿 `scripts/content_gates.py` 的 `[timing]` 打点模式。
2. 建立 golden 基线：全 28 页每页抽 ≥5 帧（含首/中/尾与慢页全帧）像素 hash 存 `cache/gfx_golden.json`；48×27 灰度 QC 比对不设防字体缺失/颜色偏移（`vtx/qc.py:62`），golden hash 才是真门槛。

### 阶段 1：低成本并行调优（半天）
3. `VTX_GFX_PAGES` 6→8（实测 6 已近 CPU 饱和，8 为轻页余量；12 需压测后决定，页轻时近线性、页重时无益），`VTX_GFX_TABS` 保持 4。预期 192.5s → ~150-165s。
4. 高争用下慢页（bench 中曾达 768ms/帧的 b1_bricks 类）确认无异常锁竞争。

### 阶段 2：canvas 批量导出改造（2-3 天，核心）
5. 扩展 `__vtx_export_png` 协议为**批量模式**：页面在 JS 侧循环 `__vtx_render(f)` + `canvas.toBlob`，攒 N 帧（如 10 帧）一次性经一条 CDP 消息回传（base64 或 binary 分帧），渲染器侧解码落盘。每帧成本目标从 ~50ms 降到 ~15-30ms。
6. DOM 页接入方式二择（各取成本小者）：
   a. 页面直接 canvas 化（重画 c5a/c5b 等慢页为 canvas 绘制，一次性投入）；
   b. SVG foreignObject 自动桥：DOM 序列化进 canvas（需 web font 内联，逐页验证字体渲染保真度——这是本方案最大不确定性，先做 1 页探路）。
7. 慢页优先：c5a_main_path、c5b_hotkey、llm_post、u3_install、g6b_endboard 五页先改，覆盖最大耗时。改造页必须通过 golden hash 逐帧比对 + 通道自带信封校验，失败自动回落截图路径并打 warning。
8. （可选加分项）静态跨度声明协议：纯函数页声明「f∈[a,b) 画面不变」的常量跨度，渲染器只渲首帧、字节复制余帧；实测平均 ~20% 帧字节级重复（最高 74%），以抽帧 hash 校验兜底。

### 阶段 3：回归与文档（半天）
9. `vtx all` 全链回归 + golden hash 全量比对；更新 `docs/DEV.md`（含本轮证伪记录）、`skill/references/gfx.md` 协议文档、runbook 基准表。

## 三、开发要求

1. 帧确定性协议（`?f=` 纯函数、同 f 同像素）不可动摇；禁止 screencast/MediaRecorder/wall-clock。
2. 所有导出路径必须可回退到现行截图路径（env 开关 + 自动回落），golden hash 是唯一放行标准。
3. 路径打标与分项计时必须保留在正式日志中，作为后续一切优化的观测基础。
4. 并行度参数保持 env 可覆盖；默认值修改必须有本机实测三档数据支撑并写入 DEV.md。
5. 改动限于 `vtx/gfx_render.py`、`vtx/vtx.py` gfx 阶段、gfx 页面 JS；不得触碰 composite/audio 阶段。
6. 防 GIL 陷阱：若批量解码落盘在 Python 侧成为新瓶颈（透明页 alpha 合成持 GIL 已实测限制 tab 扩展），解码/落盘必须走进程池。

## 四、验收要求（严格、可量化、防自夸）

> 性能验收一律**当次同机重测基线**（禁止引用历史 log），报告 p50（3 次）而非单次最好值，附分项计时日志原文。

1. **性能硬门槛**：清 `cache/gfx` 冷跑 gfx 阶段 3 次取中位，`TOTAL_WALL ≤ 110s`（基线当次重测应在 190s±15% 区间，否则说明机器状态异常需先排查）；**冲刺目标 ≤85s**（未达不判失败，但必须在报告中给出逐页分项计时与未达原因分析）。总帧数须与基线一致（12024 帧）。
2. **像素一致性硬门槛**：改造页 golden hash 逐帧全零差异（非抽样）；未改造页抽检 ≥5 帧/页零差异。比对脚本与结果 JSON 提交。
3. **分项计价验收**：日志中改造页的单帧导出成本（导航+渲染+回传+落盘）中位数 ≤35ms，且路径打标显示走 canvas 通道（非回落）。
4. **回归硬门槛**：`vtx all` 后 golden hash 全量一致；QC 75/75 通过且 `vtx qc diff` 无画面差异项。
5. **稳定性**：连续 3 次冷跑无实例崩溃、无静默回落（对已改造页）、无帧缺失断言失败；峰值内存 ≤16GB。
6. **诚实条款**：任一硬门槛未达必须写明实测数字与归因；探路实验（foreignObject 字体保真）失败也要如实记录，不得只交付成功页面的数字。
